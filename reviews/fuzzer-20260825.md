# SOTF all-app state-aware fuzzer

**Date:** 2026-08-25

**Status:** Proposed

**Scope:** Design only; no fuzzer or application source changes are included

## Decision summary

Build the first all-app fuzzer as a seeded, state-aware extension of
`sotf-dev-driver`. Reuse the current scenario runner, QA isolation, dev API,
fixtures, crash-log gate, and systemwide lab infrastructure. Add target
adapters rather than forcing every process to look like a GUI.

The default generator will choose an action whose declared preconditions are
satisfied 85% of the time and a bounded-chaos action 15% of the time. Every
choice and observation will be written to an exact NDJSON trace before the
next action. A seed is useful for rediscovery; the trace is the replay source
of truth.

Protocol v2 should be implemented once in an optional `sotf-dev-api` crate and
used by GPUI, TUI, and simulator-only mobile builds. It adds authenticated
liveness, capability discovery, allow-listed snapshots, bounded input
primitives, revisions, and telemetry while retaining the existing action,
key, selector, QA-fixture, and quit semantics.

Version 1 covers user-facing production entry points: GPUI desktop, TUI,
iOS/tvOS simulators, player and recorder CLIs, headless server mode, the
systemwide daemon, and ConfigBar. Internal QA binaries and plugin-specific
fuzzers are not all-app targets.

## Goals

- Exercise real application processes and their user-visible state machines,
  not only parsers or isolated DSP functions.
- Reproduce a failure from a preserved trace without depending on a changing
  random generator or timing accident.
- Explore more than random clicks by using runtime capabilities, current
  state, action preconditions, coverage rarity, and known workflows.
- Detect crashes, panics, invalid state transitions, stalls, hangs, and
  sustained resource growth as distinct failure classes.
- Keep runs hermetic and safe by default: loopback networking, fake audio and
  files, private runtime/config directories, and no installed HAL or physical
  mobile device.
- Produce CI-readable reports and a self-contained artifact bundle suitable
  for replay and minimization.

## Non-goals

- Replacing unit tests, property tests, protocol parser fuzzers, DSP fuzzers,
  scenario tests, or accessibility tests.
- Proving the absence of memory leaks from RSS alone. Portable growth is
  reported as suspected until a platform leak tool supplies stronger evidence.
- Fuzzing arbitrary internet services, user accounts, the user's media
  library, installed external plugins, or real audio hardware by default.
- Fuzzing release builds through a remotely reachable control interface. The
  dev API remains loopback-only and debug/QA-only.
- Treating internal benchmark, demo, fixture-generator, or `qa_*` binaries as
  user-facing app targets.

## Current baseline

The repository already contains most of the control-plane pieces required by
the design, but they are currently target-specific and scenario-oriented.

### Desktop and TUI dev APIs

The GPUI dev API runs a small HTTP/1.1 listener on a dedicated OS thread. It
forwards commands through an `mpsc` channel and waits for GPUI-main-thread
replies. Protocol v1 exposes `/action`, `/query`, `/key`, selector-based click,
hover, drag and scroll, deterministic resize and screenshot, accessibility,
QA fixture routes, `/health`, and `/quit`. Tracked selectors retain rendered
bounds and semantic state. Current `/health` is still fulfilled through the
main thread, so it cannot distinguish a healthy listener from a stalled UI.

The TUI has a separate implementation of the same basic HTTP server, command
and reply envelopes, action/query/key routes, QA seeding, health, and quit. It
also supports a headless test backend when a dev API port is supplied and
stdout is redirected. Its input and observation surface is intentionally
narrower than GPUI's. The duplicated HTTP parser and wire types can drift.

Both APIs are feature-gated. GPUI additionally has checks intended to keep the
dev API out of release recipes and requires a QA launch before the listener is
started. Protocol v2 must preserve and strengthen those controls for all
consumers.

### Driver, scenarios, and fixtures

`sotf-dev-driver` currently supports a line-based scenario DSL plus a
`run-suite` command. Its verbs cover actions, queries/assertions, polling,
keys and text, tracked-element interactions, screenshots, accessibility, and
several UI layout assertions. The suite runner starts a fresh process per
scenario, creates an isolated QA directory, assigns a loopback port and run
ID, validates the process identity returned by `/health`, installs requested
fixtures, invokes `/quit`, and kills a process that does not stop promptly.

The checked-in QA surface includes demo audio, fake recording capture and
faults, offline Headphone EQ and Spinorama discovery, and RoomEQ recordings
and optimizer/UI fixtures. The runner copies fixture data into the scenario
artifact tree rather than granting the app access to arbitrary checkout or
user paths.

Suite output already includes process stdout/stderr, GPUI's structured log,
JSON, JUnit, and HTML summaries. A clean-log gate reports unapproved
`ERROR`/panic lines. This is a useful baseline, but it does not yet retain an
action-by-action write-ahead trace, resource samples, stack samples, or a
normalized failure signature.

### Other application surfaces

- The iOS and tvOS crates contain GPUI-based Rust shells plus their native
  application bridges and platform smoke tests. They do not yet expose the
  common dev protocol or a simulator fuzzer adapter.
- The player and recorder CLIs are already spawned by hermetic Rust integration
  tests that inspect arguments, exit status, stdout, and stderr. They need a
  process/stdin/signal adapter, not a GUI protocol.
- `sotf-desktop --server` starts the headless SOTF API, MPD, and DLNA services
  from the shared player layer and blocks until shutdown. Existing server tests
  cover configuration, loopback safety, authentication, and protocol behavior,
  but the dev driver does not yet generate cross-protocol server sessions.
- The systemwide daemon has bounded JSON-line IPC, private socket/runtime path
  overrides, null/lab audio-driver support, a `LabDriver`, and subprocess
  scenario tests that avoid a real HAL install. ConfigBar has a native IPC
  client and Swift model/UI tests. Neither is connected to the dev driver.

## Architecture

The fuzzer is a supervisor with target-specific adapters around a shared
generator and artifact pipeline:

```text
surface manifest + seed
          |
          v
state-aware generator ---> write-ahead trace ---> artifact store/reporters
          |                       ^                         ^
          v                       |                         |
    target adapter ----------> observation ---------- resource sampler
          |
          +-- dev API: GPUI/TUI/mobile
          +-- process: CLI/server
          +-- IPC/bridge: daemon/ConfigBar
```

The supervisor owns process lifetime, deadlines, resource sampling, logging,
failure classification, replay, and minimization. An adapter owns target
launch details, capability conversion, action execution, snapshots, target
invariants, graceful shutdown, and cleanup. Generator code never calls a
platform tool directly.

### Shared optional `sotf-dev-api` crate

Add `crates/sotf-dev-api` as an optional dependency of app crates that expose
the protocol. It should contain:

- serde wire types, protocol/limit constants, reply metadata, authentication,
  and strict HTTP parsing;
- the loopback listener, bounded connection/command queues, deadlines, and
  listener-side telemetry;
- capability, snapshot, tracked-element, accessibility, and resource-counter
  schemas;
- target hooks/traits for dispatch, state capture, and supported fixtures;
- a reusable contract-test harness.

It must not own player business logic or GPUI/TUI widget state. Each app
implements the target hooks and allow-list. The crate is enabled only by an
explicit `dev-api`/QA feature and must contain compile-time guards against a
release build. Mobile enables it only for simulator debug/QA builds. Release
recipes get tests proving that the feature is absent. The listener always
binds a loopback address and refuses wildcard or LAN binds.

### Protocol v2 routes

| Route | Thread dependency | Purpose |
| --- | --- | --- |
| `GET /live` | listener only | Prove that the listener and process can answer without entering the UI/event loop. |
| `GET /capabilities` | listener/static registry | Return target ID, build/protocol versions, registered actions and queries, input primitives, fixtures, limits, and manifest version. |
| `GET /snapshot` | target event loop | Return an allow-listed, revisioned state and accessibility snapshot. |
| `GET /health` | target event loop | Preserve v1 readiness semantics and identity/build information. |
| `POST /action` | target event loop | Preserve named action and optional JSON payload semantics. |
| `GET /query` | target event loop | Preserve allow-listed path queries for scenarios and compatibility. |
| `POST /key` | target event loop | Preserve target-specific key syntax. |
| selector routes | target event loop | Preserve click/hover/drag/scroll and semantic selector behavior where supported. |
| coordinate routes | target event loop/platform bridge | Add pointer move/button, touch begin/move/end, bounded scroll, and remote input where capabilities advertise them. |
| QA fixture routes | target event loop | Preserve typed, allow-listed deterministic fixture installation. |
| `POST /quit` | target event loop | Preserve graceful application shutdown. |

The current paths and payloads remain valid. Updated scenario commands attach
v2 authentication and ignore additive reply fields, so existing `.scn` files
do not need to change. A target must not advertise an input primitive that its
adapter cannot deliver faithfully.

Coordinate inputs must contain finite numbers and be clamped or rejected
against the latest viewport revision. Touch identifiers, simultaneous touches,
button values, scroll deltas, key/text length, and remote commands have small
hard bounds advertised by `/capabilities`. Bounded chaos can cross a semantic
precondition; it cannot request unbounded allocation or an out-of-sandbox
operation.

### Authentication, parser, and queue bounds

The supervisor generates a high-entropy run ID and passes it through inherited
process configuration, never argv. Every protocol-v2 request includes it in
`X-SOTF-Dev-Run-ID`; missing or mismatched credentials receive `401` before a
command is queued. The value is not placed in URLs or normal logs. This is a
cross-run/stale-listener defense, not a replacement for the loopback and build
guards.

The initial hard limits should be explicit constants and reported as
capabilities:

- 4 KiB request line, 64 headers and 32 KiB total headers;
- 256 KiB ordinary command bodies and 2 MiB typed fixture bodies;
- 4 MiB snapshot/accessibility response;
- two-second socket read/write timeout and configurable five-second command
  deadline;
- at most 16 active connections and a 64-command target queue by default.

Reject duplicate/conflicting `Content-Length`, unsupported transfer encodings,
invalid UTF-8 where text is required, oversized bodies before allocating them,
and trailing bytes. Close each response connection. A full command queue
returns `429` with telemetry rather than blocking the listener. Parser and
fixture limits are testable policy, not best-effort documentation.

### Response metadata and telemetry

All v2 replies retain `ok`, `value`, and `error` compatibility and add a
`meta` object containing:

- monotonically increasing command sequence;
- state revision before and after dispatch, plus render/accessibility revision
  when applicable;
- monotonic accept, queue, dispatch, and total durations;
- queue depth, queue high-water mark, rejected-command count, and target-loop
  heartbeat age.

Use monotonic durations for classification and wall-clock timestamps only for
human correlation. Sequence numbers are per run. State revisions must advance
for relevant asynchronous changes as well as direct dev commands; otherwise a
fuzzer would incorrectly treat background work as a stable state.

### Capabilities and snapshots

`/capabilities` is the runtime truth. At minimum it returns:

- target ID, platform, process/build identity, protocol version, and enabled
  debug features;
- action names and families, query paths, selector/accessibility support, and
  platform input primitives;
- supported QA fixtures and fake backends;
- protocol and input limits;
- surface-manifest schema/version and unsupported optional capabilities.

`/snapshot` exposes only fields deliberately registered by the target. It
contains current screen/mode, open dialogs and overlays, stable selections,
playback/recording/server state, state/render revisions, outstanding async
activities with age/status, tracked selectors with bounded geometry and
semantic flags, accessibility focus/tree summary, and target resource
counters. No arbitrary reflection, filesystem browsing, secrets, raw media
metadata, or user-entered text is allowed.

The snapshot also returns a canonical `state_hash`. Hash only stable,
allow-listed semantic fields; exclude timestamps, durations, process IDs,
resource totals, and animation coordinates. Store the unhashed allow-listed
state with failure artifacts so a collision cannot hide diagnosis.

## Driver extensions

Add three subcommands without removing legacy scenario or suite operation:

```text
sotf-dev-driver fuzz --target desktop-gpui --seed 42 --steps 10000
sotf-dev-driver replay <artifact-dir>/replay.toml
sotf-dev-driver minimize <artifact-dir>/replay.toml
```

`fuzz` accepts a target or checked-in target set, seed, step/time budgets,
fixture profile, artifact directory, opt-ins, and worker count. The default is
one worker. Multiple workers are explicit because GUI processes, simulators,
audio backends, and ConfigBar have singleton or resource-contention behavior.
Worker seeds are deterministically derived from the root seed and worker index.

`replay` launches the recorded target/build configuration, validates the
capability fingerprint, installs the recorded fixture profile, and executes
the resolved trace exactly. Capability drift is an explicit error unless the
operator selects a diagnostic best-effort mode.

`minimize` repeatedly launches a clean target and reduces a failing trace. It
first removes contiguous chunks, then individual actions, delays, and payload
fields, and finally shrinks numbers, text, coordinate paths, and repeated input.
Crash and hang traces are minimized automatically after artifact capture.

### Serializable model

All persisted models use versioned serde schemas and tagged enums. The core
records are:

- `TargetSpec`: target ID, adapter kind, executable/app identity, platform,
  fixture profile, environment allow-list, endpoints, run ID hash, and
  capability fingerprint;
- `Action`: action ID/family, state-valid or chaos class, precondition ID,
  target-specific typed payload, timeout, and RNG stream/cursor;
- `Observation`: command reply and metadata, state/snapshot revisions and hash,
  process status, new logs/crash files, resource sample, coverage deltas, and
  screenshots or accessibility changes;
- `Failure`: class, normalized signature, first failing sequence, evidence,
  target/build identity, confirmation count, and artifact references.

Unknown enum variants must fail closed in normal replay. Schema migration is a
separate, explicit conversion so old traces are never silently reinterpreted.

### Process and filesystem isolation

Each run gets a directory such as `target/sotf-fuzz/<run-id>/`; each worker and
case gets a child directory containing its QA/config, runtime, library, temp,
logs, and artifacts. Paths passed to targets are canonical descendants of that
directory. Symlinks and `..` escapes are rejected when fixtures are staged.

Every process gets a unique run ID and endpoint set. Prefer binding port zero
and atomically publishing the selected loopback endpoint into the private run
directory. Where a target requires a preselected port, allocate it immediately
before spawn and require the run-ID handshake so a stale listener cannot pass
readiness. A case owns and reaps its complete child-process tree.

The supervisor strips account/network credentials and unrelated SOTF config
variables from the child environment, then adds only the adapter allow-list.
It records the names of inherited variables but redacts sensitive values.

### Exact NDJSON write-ahead trace

The trace is an append-only sequence with a schema version. It begins with
`run_start`, target/build identity, seed, generator version, capabilities,
surface-manifest digest, limits, and fixture digest. For each step:

1. Append and flush an `action_intent` containing the fully resolved typed
   action, classification, precondition result, sequence, RNG cursor, and
   preceding state revision/hash.
2. Dispatch exactly that action.
3. Append an `observation` with reply/timing, snapshot and resource deltas,
   logs, coverage, and any failure candidate.
4. Append confirmation and cleanup events before closing the trace.

Writing the intent before dispatch preserves the last action when the process
crashes or the machine loses power. Replay consumes resolved actions, not the
generator, so later weight or RNG changes do not change old reproductions.
Trace flushing happens in the supervisor and never on an audio callback.

## State-aware generation

### Checked-in surface manifest

Add a versioned manifest under `crates/sotf-dev-driver/fuzz/` that describes
target screens/modes/dialogs, action families, coarse preconditions, recovery
actions, invariants, fixture requirements, semantic coverage keys, and known
workflow edges. Runtime capabilities are intersected with this manifest.
Missing runtime actions become manifest-drift diagnostics; newly registered
actions remain visible but receive conservative weights until classified.

The manifest contains no executable expressions. Preconditions use a small
typed vocabulary over allow-listed snapshot fields, for example equality,
membership, selector visibility/enabled state, async-idle, and process phase.
This keeps evaluation deterministic, serializable, and reviewable.

### 85% valid / 15% bounded chaos

For every eligible action selection, a seeded integer draw chooses:

- **85% state-valid:** choose only actions whose manifest preconditions match
  the latest snapshot. A rejection here is `valid_action_rejection`, not
  ordinary fuzz noise.
- **15% bounded chaos:** choose a capability-supported action that may violate
  a semantic precondition or use a boundary payload. Examples include a stale
  selector, a duplicate start/stop, empty or maximum-length text, edge
  coordinates, an unexpected but bounded protocol message, or rapid toggles.

Chaos never expands the permission boundary. It may not select arbitrary
paths, hosts, plugins, devices, signals, body sizes, or native platform APIs.
If no valid action exists, the adapter first attempts a declared recovery or
restart; it does not relabel chaos as valid. Metrics report the achieved mix
over eligible selections.

### Coverage-seeking weights

Maintain counters for screens, modes, dialog/overlay states, selectors,
accessibility roles, action families, state hashes, state transitions, async
outcomes, and target-specific workflow edges. Weight candidates toward rare
and unseen keys, with a bounded novelty bonus and decay so one hard-to-reach
state cannot monopolize the run.

Keep interesting trace prefixes when they discover a new state hash,
transition, selector set, action family, invariant boundary, or failure
signature. Corpus entries are traces plus fixture/config identity, not memory
dumps. Reaching an entry replays its prefix in a clean process; v1 does not
require unsafe in-process state restoration.

## Target adapters

### GPUI desktop

Use the shared v2 listener and the existing action/query/selector,
accessibility, screenshot, resize, and QA fixture implementations. The GPUI
adapter models screens, dialogs, tracked semantic elements, focus, player
state, recording/RoomEQ async work, and current viewport. It generates both
semantic actions and bounded pointer/keyboard input. Semantic actions remain
the primary route because they are stable across layout and theme changes;
coordinate input specifically covers hit testing, focus, drag, scroll, and
responsive layout.

### TUI

Use the same wire types, authentication, liveness, capabilities, snapshots,
and response metadata, with TUI-owned dispatch and state models. Input is
crossterm key/resize/paste where the backend supports it; pointer actions are
not advertised unless mouse handling is actually enabled. Run with a private
QA directory and deterministic headless backend by default, with selected PTY
runs retained for terminal integration coverage.

### iOS and tvOS simulators

Compile the shared dev API only into simulator debug/QA builds. The adapter
uses `simctl` to select a named runtime/device profile, boot if necessary,
install, launch with a private QA container and run ID, capture logs and
screenshots, obtain the app PID, and terminate/erase only fuzzer-owned devices.
Physical devices are not an implicit fallback.

The HTTP API supplies semantic actions and snapshots. iOS touch sequences use
a debug-only native platform bridge that validates touch IDs, coordinates,
phase transitions, count, and duration before delivering GPUI platform input.
tvOS maps a bounded command enum onto the native Siri Remote/focus input bridge.
`simctl` remains lifecycle/diagnostic plumbing; do not assume it can faithfully
synthesize every touch or remote gesture itself.

If Xcode, the requested simulator runtime, bridge feature, or host permission
is absent, return a structured skip with the missing capability.

### Player and recorder CLIs

Generate typed argv, stdin chunks/EOF, bounded waits, and an allow-listed set
of lifecycle signals against the actual shipping binaries. Use fixture media,
temporary outputs, deterministic clocks where needed, and fake input/output
device backends. Never enumerate or open real audio devices in a default run.

The adapter synthesizes snapshots from process phase, exit status, structured
test-backend events, bounded stdout/stderr parsing, output artifacts, and fake
backend counters. Each generated CLI case starts clean; multi-step sessions
are used only for commands that genuinely consume stdin or respond to signals.
Arguments remain typed by the manifest rather than arbitrary shell strings,
and processes are launched without a shell.

### Headless MPD/DLNA/SOTF server

Launch the real server mode with a private database/library/config and fake
player/device backend. Bind all services to unique loopback ports. Disable LAN
discovery and multicast by default. Generate stateful MPD command sessions,
authenticated SOTF API requests, bounded HTTP framing, and bounded DLNA
HTTP/XML/SOAP handler inputs. Cross-protocol sequences should verify that all
frontends observe one coherent player/library state.

Protocol chaos includes fragmentation, pipelining where supported, invalid
ordering, boundary lengths, XML depth/attribute/entity policy, disconnects,
and slow-but-deadline-bounded clients. It does not contact discovered network
devices or arbitrary URLs. The server adapter enforces loopback again after
configuration is loaded and fails an invariant before launch if a listener
would escape it.

### Systemwide daemon

Launch `sotf-daemon` with private socket and runtime paths and the existing lab
driver, never a real HAL driver by default. Generate bounded JSON-line IPC,
including valid stateful configuration/transport sequences and malformed
framing within the daemon's hard line limit. Observe daemon snapshots,
generation changes, engine-ready transitions, metering shape, driver
configuration handshakes, socket ownership, and cleanup/restart behavior.

The adapter asserts systemwide invariants: one owner per private runtime,
coherent configuration generations, complete audio frames, bounded clients,
no stale socket after exit, child-thread/process cleanup, and rollback after
injected failures. Real HAL installation or the user's system output device is
never required by the default target.

### ConfigBar

Add a QA-only intent/state bridge around ConfigBar's model/controller boundary.
It accepts a typed set of user intents and returns allow-listed generations,
pending mutations, daemon connection state, meters, graph state, and visible
errors. It points only at the fuzzer-owned daemon/runtime. This is the main
high-volume surface because it is deterministic and avoids brittle menu
coordinates.

Retain a smaller accessibility-driven UI layer to open/close the menu, invoke
representative controls, verify focus/labels/enabled state, and confirm that
bridge-visible model changes reach the rendered UI. The bridge and any test
hooks are compiled only in QA builds. Production ConfigBar behavior continues
to use the real IPC client.

## Failure detection

Failure classes stay separate in reports even when one event produces several
pieces of evidence.

| Class | Classification rule |
| --- | --- |
| `unexpected_exit` | Process exits before a requested/expected terminal state. |
| `signal_or_exception` | Unix signal, Windows exception, macOS crash report, or equivalent abnormal termination. |
| `panic_or_error_log` | Unallowlisted structured error/panic or recognized panic text, even if exit status is zero. |
| `valid_action_rejection` | An 85%-path action whose recorded precondition was true is rejected by the target. |
| `invariant_violation` | A named generic or target invariant evaluates false in two consistent snapshots, or immediately when the state is terminally impossible. |
| `command_timeout` | One command misses its deadline while liveness/snapshot probes still classify the process. |
| `main_loop_stall` | `/live` answers but `/snapshot` and target-loop heartbeat fail confirmation. |
| `whole_process_hang` | Process remains alive but `/live` and target progress both fail confirmation. |
| `resource_leak` | Threads, descriptors/handles, or child processes show sustained retained growth over configured thresholds. |
| `suspected_memory_leak` | Robust memory-growth and retained-growth gates both pass after warmup. |

Expected rejection from the 15% chaos path is an observation and coverage key,
not a failure, unless the response violates protocol, timing, or state
invariants. A crash following a chaos action is still a crash.

### Stall and hang state machine

Probe `/live` directly on the listener and `/snapshot` through the target loop.
Use configurable deadlines with conservative defaults (one-second probe
cadence, two-second probe timeout, three consecutive misses):

1. If the action times out, probe `/live` immediately.
2. If `/live` succeeds but `/snapshot` repeatedly fails or the loop heartbeat
   is stale, classify `main_loop_stall`.
3. If `/live` fails while the OS still reports the process alive, confirm with
   process/resource progress and two more probes, then classify
   `whole_process_hang`.
4. If the process exited, classify the exit/signal instead of hang.
5. Before termination, capture the last snapshots, metrics, logs, crash files,
   and an external all-thread sample. Then attempt graceful quit, followed by
   adapter-scoped termination and process-tree reap.

Enable `parking_lot` deadlock detection only in dev/QA builds and run its
watchdog outside the target event loop. The watchdog writes detected cycles
and thread IDs to a pre-opened artifact channel/file but does not terminate the
process itself. This evidence enriches the hang signature; the external sample
is still required because not every stall is a `parking_lot` deadlock.

Use `sample` on macOS before killing a stuck process. Linux and Windows
providers should capture the best available all-thread stack/minidump through
an explicit provider hook, falling back to safe process metadata when ptrace
or debugging permission is unavailable. Missing sampling permission is
recorded in artifacts and does not erase the hang.

### Invariants and log evidence

Generic invariants include monotonic command/state revisions, matching run
identity, bounded queues and response sizes, finite numeric state, no escaped
paths/listeners, one owned process tree, and clean expected shutdown. Target
manifests add domain invariants such as valid selection indexes, coherent
dialog/focus state, server frontend agreement, and systemwide generation and
driver readiness rules.

Build on the current clean-log gate, but stream logs incrementally and classify
structured severity where available. Normalize panic and crash signatures from
message plus stable top frames, stripping addresses, line-number churn, run
paths, and secrets. Scenario-specific allowlists remain narrow and are copied
into run metadata.

### Portable resource and memory sampling

The supervisor samples the target and its owned process tree at a fixed cadence:
RSS/working set, virtual memory, CPU time/utilization, thread count,
descriptor/handle count, and child-process count. Platform providers use native
read-only process APIs; unavailable fields are `null` with a reason, never
invented as zero.

Discard startup/warmup and compute a robust Theil-Sen slope over steady-state
RSS samples. Report `suspected_memory_leak` only when both conditions hold:

```text
RSS slope > 1 MiB/minute
retained RSS growth > max(32 MiB, 10% of steady-state baseline)
```

The baseline is the median of the first steady-state window and retained growth
uses the median of the final window, preventing a single peak from deciding the
result. Preserve raw samples and window selection. Virtual-memory and CPU
growth are diagnostic unless a target manifest defines a separate invariant.

Thread, descriptor/handle, and child-process leaks use per-target absolute
budgets plus sustained retained growth across at least three final windows.
Short-lived spikes and known helper processes are recorded but do not fail the
run. A child that outlives its owning case is always a cleanup invariant
failure even if the numeric leak threshold is not reached.

### macOS leak profile

Weekly macOS leak runs use a dedicated QA build with the system allocator,
because alternate allocators can hide allocations from Apple tooling. Enable
`MallocStackLogging`, capture a post-warmup baseline and pre-exit final `leaks`
report, and take `sample` output at both points. Compare final findings with
the baseline rather than failing on process-wide singletons initialized once.

Optionally collect an Instruments Allocations/Leaks trace through `xctrace`
when the host has the template and permissions. This is additive evidence, not
a prerequisite for the portable classifier. Linux and Windows keep the same
portable sampling and expose provider hooks for sanitizers, Valgrind/heaptrack,
WPR/ETW, debugger dumps, or future CI-specific tooling.

## Failure artifacts, replay, and minimization

Preserve at least:

```text
run.json                 target/build/seed/config/fixture identity
capabilities.json        exact runtime capability response
surface-manifest.*       resolved manifest and digest
trace.ndjson             exact write-ahead intents and observations
snapshots/               bounded ring plus first/failure/final snapshots
coverage.json            counters, transitions, corpus reasons
metrics.ndjson           raw process/resource samples
logs/                    stdout, stderr, structured and platform logs
screenshots/             periodic and failure frames where supported
crash/                   crash reports/minidumps and normalized signature
hang/                    listener/loop state and external thread samples
leaks/                   portable classifier plus platform leak reports
replay.toml              self-contained replay configuration
summary.json
junit.xml
summary.html
```

Keep a bounded in-memory/on-disk ring of recent snapshots and screenshots, then
pin the relevant window on failure. Always preserve the seed, but do not claim
that seed-only replay is exact.

The failure signature determines minimization equivalence: normalized exit
signal/exception and frames for crashes; stall class, blocked sequence/action,
and stack fingerprint for hangs; invariant ID and normalized state for
invariants. A minimized crash or hang candidate is accepted only when the same
signature occurs in two of three clean runs. Store all three outcomes. Leave
the original trace untouched and emit `trace.min.ndjson` plus its own replay
file. Memory/resource leak minimization is optional/manual in v1 because its
long windows make automatic delta debugging disproportionately expensive.

## Safety and opt-ins

Defaults prohibit:

- physical audio input/output and hardware enumeration;
- non-loopback network binds, discovery, or account access;
- loading installed external plugins;
- installing/enabling the real macOS HAL driver;
- physical iOS/tvOS devices;
- user config/library/runtime paths and arbitrary filesystem inputs.

Each expansion requires a separate explicit flag and capability, for example
`--allow-hardware-audio`, `--allow-network`, `--allow-external-plugins`,
`--allow-hal-install`, or `--allow-physical-device`. These flags are not implied
by `--target all`, CI schedule, replay, or minimization. Artifacts prominently
record active opt-ins.

Redact authentication headers, run IDs, API tokens, credentials, home-directory
prefixes, and non-fixture media metadata before report generation. Keep raw
local artifacts only when an explicit secure-artifact setting requests them;
portable/uploaded reports use redacted copies. Unit tests must cover nested
JSON, NDJSON, URLs, XML, logs, environment dumps, and path redaction.

## Validation plan

### Unit tests

- deterministic action and worker-seed generation across repeated runs;
- manifest parsing, capability intersection, and every precondition operator;
- exact 85/15 branch selection over controlled seeded draws and reporting when
  no valid action exists;
- rarity/novelty weighting without starvation or unbounded weights;
- strict HTTP request/header/body/response limits, duplicate length, timeouts,
  auth failure, bounded queue saturation, and coordinate limits;
- state-hash canonicalization and revision/timing metadata;
- hang/stall state-machine transitions and exit-vs-hang precedence;
- Theil-Sen slope, warmup/final windows, the dual memory threshold, and
  thread/descriptor/handle/child leak classification;
- write-ahead truncation recovery, exact replay, capability drift, and schema
  rejection/migration;
- delta minimization and two-of-three signature confirmation;
- artifact path containment and recursive secret/path/metadata redaction.

### Shared protocol contract tests

Run one reusable contract suite against GPUI, TUI, and simulator mobile hooks.
It validates route/payload compatibility, authentication, limits, sequence and
revision monotonicity, capabilities, snapshots, queue pressure, graceful quit,
and that `/live` still responds while a synthetic target-loop handler is
blocked. Target-specific capabilities may differ; the common envelope may not.

### Synthetic failure fixtures

Provide dev-only fixture targets/modes that crash or panic after sequence N,
stall only the main loop, hang the listener/process, reject a declared-valid
action, violate a named invariant, retain memory, leak threads/descriptors, and
leave a child process. These verify the supervisor and artifact pipeline
without waiting for a real regression.

### Hermetic integration tests

- GPUI and TUI: fixed-seed navigation, dialog, selector/key, async fixture, and
  replay tests in isolated QA directories.
- CLI: typed argv/stdin/signal cases with fake devices/files and output-path
  containment.
- Server: loopback-only stateful MPD, authenticated SOTF API, bounded HTTP/XML,
  and cross-frontend state agreement.
- iOS/tvOS on macOS: simulator launch/identity, semantic API, touch/remote
  bridge, crash/log/screenshot capture, cleanup, and structured missing-runtime
  skips.
- Systemwide: lab-driver IPC sequences, generation/rollback/engine-ready
  invariants, restart/socket cleanup, and failure injection.
- ConfigBar on macOS: QA bridge model sequences plus a small accessibility UI
  suite against the fuzzer-owned daemon.

## CI and reporting

### Pull-request smoke

- Unit and shared protocol contract tests on every affected PR.
- Fixed checked-in seeds for supported desktop/TUI/CLI/server adapters, one
  worker, short step/time budgets, and no external opt-ins.
- Synthetic crash, stall, hang, and growth fixtures.
- Fail only on confirmed crash/signal, panic/error log, valid-action rejection,
  invariant, stall/hang, cleanup leak, or configured resource threshold.

### Nightly

- Rotate deterministic seeds derived from commit and date for desktop, TUI,
  CLI, and headless server targets on supported hosts.
- Run longer crash/deadlock campaigns and at least one multi-hour single-worker
  soak, retaining interesting coverage prefixes.
- Run deadlock-watchdog builds where available and automatically minimize
  confirmed crash/hang traces.

### Weekly macOS

- System-allocator `MallocStackLogging` leak profiles for desktop, ConfigBar,
  and the systemwide lab target, with baseline/final `leaks` and `sample`.
- iOS and tvOS simulator campaigns across the supported runtime matrix.
- Longer systemwide/ConfigBar failure-injection and restart campaigns.
- Optional `xctrace` collection on a suitably provisioned runner.

Every tier emits JUnit for CI annotations, versioned JSON for aggregation, and
a static HTML summary showing target/seed, outcome, failure signatures,
coverage deltas, resource charts, skips, opt-ins, artifact links, and replay
commands. Skips are visible in all three formats.

## Rollout and ownership

Open one tracking issue before implementation. It should link this design,
record v1 acceptance criteria, own the target/fixture/safety matrix, and split
the work into staged PRs:

1. Shared `sotf-dev-api` protocol, contract harness, supervisor models,
   artifact writer, resource sampler, and synthetic failure fixtures.
2. GPUI/TUI protocol-v2 migration plus desktop/TUI fuzz adapters, replay, and
   crash/hang minimization.
3. iOS/tvOS simulator protocol hooks, platform input bridges, and adapters.
4. Player/recorder CLI and headless SOTF API/MPD/DLNA adapters.
5. Systemwide lab/IPC adapter and ConfigBar QA bridge/accessibility layer.

Keep each PR within existing crate ownership boundaries. If implementation
later changes `sotf-engine` or `sotf-plugins`/plugin-host behavior, those changes
remain dedicated PRs and require the repository's specialized code-review
workflow before merge. The fuzzer project does not relax audio-thread safety,
allocation, HAL, or external-plugin review requirements.

## V1 acceptance criteria

- Every in-scope target either completes a hermetic smoke run or emits a
  structured, justified skip on each supported CI host.
- Repeated runs with the same seed/build/manifest produce the same resolved
  action trace until an observation genuinely differs; the saved trace replays
  independently of generator changes.
- GPUI, TUI, and mobile share protocol wire/parser code and pass one contract
  suite; `/live` distinguishes listener liveness from target-loop liveness.
- Default runs use one worker and cannot touch non-loopback networks, user
  data, real audio devices, installed plugins, HAL installation, or physical
  mobile devices.
- All failure classes generate normalized signatures and complete artifacts;
  crash/hang traces are minimized only after two-of-three confirmation.
- Memory suspicion uses both the 1 MiB/min robust slope and retained-growth
  threshold, while threads, descriptors/handles, and child processes are
  tracked separately.
- PR, nightly, and weekly jobs publish JUnit, JSON, and HTML summaries with
  replay configuration and explicit skip/opt-in reporting.
