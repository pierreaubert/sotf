# Server Streaming and Mobile Player Plan

Tracking issue: #70

Date: 2026-05-27

## Goal

The server crate has several promising pieces, but it does not yet form a dependable streaming product. This plan separates what exists today from what must change to support:

- streaming in from another SOTF/MPD server, HTTP/radio/HLS, Spotify, Tidal, and classical paid services;
- streaming out from one machine to another;
- safe LAN exposure, pairing, firewall guidance, and port management;
- a first-rate iPhone/iPad player and remote-control experience.

## Current State: Streaming In

### SOTF / MPD Peer Input

Relevant code:

- `crates/sotf-server/crates/sotf-federation/src/mpd_provider.rs`
- `crates/sotf-server/crates/sotf-streaming/src/mpd_source.rs`
- `crates/sotf-engine/src/decoder/core.rs`

What works:

- `MpdProvider` can connect to an MPD server over plain TCP, read albums/tracks, and create `mpd-stream://host:control_port:httpd_port/path` URLs.
- `MpdStreamSource` can tell the remote MPD instance to clear/add/play a track, then reads MPD's `httpd` output through `HttpMediaSource`.
- MPD command injection hardening is partially present: command values are quoted, control characters are rejected, and credentials are not embedded in provider-built URLs.

Main gaps:

- The provider has an `MpdClientAuthMode::Ssl` setting in persisted config, but `MpdProvider::connect` always uses plain `TcpStream`; no TLS client path is wired.
- Provider-built `mpd-stream://` URLs intentionally omit passwords, but `MpdStreamSource` only knows how to authenticate if a password query parameter is present. That means password-protected peer streaming will fail unless credentials are reintroduced into URLs or a secure out-of-band resolver is added.
- The design depends on the remote server exposing a separate MPD `httpd` output port. There is no SOTF-native HTTPS/range streaming endpoint yet.
- Playback is invasive on the remote MPD server: the client clears its queue and starts playback to obtain the stream. That is not acceptable as a general peer-library protocol.

### HTTP, Internet Radio, and HLS

Relevant code:

- `crates/sotf-server/crates/sotf-streaming/src/http_source.rs`
- `crates/sotf-server/crates/sotf-streaming/src/icy.rs`
- `crates/sotf-server/crates/sotf-streaming/src/hls.rs`

What works:

- `HttpMediaSource` supports blocking HTTP reads, range-based seeking when advertised, ICY metadata stripping, content-type hints, a 128 KiB read-ahead buffer, and reconnect attempts.
- The engine can decode `AudioSource::Url` through this path when the `streaming` feature is enabled.

Main gaps:

- `HlsSource` is only `pub struct HlsSource;`; HLS is not implemented despite the feature flag and README language.
- HTTP streaming is a low-level `MediaSource`, not a service layer. There is no auth header injection, expiring URL refresh, redirect policy, per-source timeout config, cache, metrics, or surfaced buffering state for UI.
- ICY metadata is parsed but dropped by `create_decoder_from_source`; there is no UI/event path for live title updates.

### DLNA / UPnP Input

Relevant code:

- `crates/sotf-server/crates/sotf-federation/src/dlna_provider.rs`
- `crates/sotf-server/crates/sotf-dlna/src/discovery.rs`

What works:

- Discovery can search SSDP for MediaServers.
- `DlnaProvider` can fetch a device description, locate `ContentDirectory`, browse pages, parse DIDL-Lite containers/items, and turn track resources into `AudioSource::Url`.
- Blocking network work is moved to `spawn_blocking`.

Main gaps:

- The SOAP/HTTP parser is hand-rolled and still does unbounded response reads in provider-side helpers.
- Eventing is not implemented, so library changes require full refresh/polling.
- Only plain HTTP is expected. That is normal for DLNA, but it must be documented as LAN-only and never exposed through router port forwarding.

### Spotify

Relevant code:

- `crates/sotf-server/crates/sotf-services/src/spotify.rs`
- `crates/sotf-server/crates/sotf-services/src/service.rs`

What works:

- The optional `spotify` feature uses `librespot` to authenticate with username/password, start track playback, and expose a PCM reader.
- The PCM channel has backpressure and clamps samples.

Main gaps:

- Search, album search, and album tracks are stubs returning empty vectors.
- There is no session cache, OAuth/device flow, Connect device surface, service provider registration in federation scan, or user-facing credential flow.
- Spotify's official iOS SDK controls playback in the Spotify app and has policy constraints: it supports on-demand playback for Premium users, but Spotify states that platform content must remain in its original form and cannot be used for commercial streaming integrations. This does not mean that every product-level Spotify + DSP experience is impossible: Roon is a useful counterexample that can apply DSP in a Spotify/Connect-style playback chain. The important distinction for SOTF is whether the implementation is provider-approved and supportable, versus promising raw unofficial stream extraction into the SOTF engine.

Recommendation:

- Keep Spotify outside the current server foundation work and re-evaluate it as a dedicated provider-approved integration. Do not block local/server/DLNA/iOS work on it.
- When revisiting Spotify, evaluate both native/Connect-style control and DSP-capable playback architectures explicitly instead of assuming the only options are "no DSP" or "raw stream extraction".

### Tidal

Relevant code:

- `crates/sotf-server/crates/sotf-services/src/tidal.rs`

What works:

- The optional `tidal` feature can validate an access token, search tracks/albums, get album tracks, and resolve a direct stream URL.
- It bounds JSON bodies and redacts tokens in `Debug`.

Main gaps:

- `DEFAULT_CLIENT_ID` is empty, device-code auth only returns a "visit this URL" error and does not poll or persist refresh tokens.
- The streaming endpoint path is code-owned and brittle; it should be validated against current TIDAL developer terms/SDK support before productizing.
- There is no federation provider that turns a configured Tidal source into browsable/searchable albums and playable `AudioSource`s.

Recommendation:

- Treat Tidal as a partner/API integration, not a guaranteed generic raw-stream provider. Use the official API/SDK path where possible and gate full-track playback behind credentials, subscription region, and legal review.

### Other Classical Paid Services

Current code has source config variants for `Tidal` and `Spotify`, but not Qobuz, Apple Music/Classical, IDAGIO, Presto Music, or other classical-first services.

Provider reality:

- Apple Music can be integrated on Apple platforms through MusicKit, including catalog access and playback support, but that is native platform playback rather than raw PCM for SOTF DSP.
- Qobuz publishes API terms/guidelines, but a stable public self-serve developer API was not found in this pass. Treat Qobuz as partner-gated until proven otherwise.
- Tidal has a public developer portal/API-SDK story, but full playback rights and SDK scope need confirmation.
- IDAGIO/Presto Music should be assumed unavailable for direct streaming until a public or partner API is confirmed.

Classical-specific gap:

- The current library/provider model has some metadata fields such as composer, but the player experience is album/track centric. A serious classical player needs first-class work, movement, composer, conductor, ensemble, soloist, label, catalog number, recording date, release date, and multiple-work album handling.

## Current State: Streaming Out

### MPD Server

Relevant code:

- `crates/sotf-server/crates/sotf-mpd/src/server.rs`
- `crates/sotf-player/src/server.rs`
- `crates/sotf-player/src/federation_config.rs`

What works:

- `sotf-mpd` implements an MPD-compatible TCP control protocol with line caps, password redaction, command-list support, and optional TLS feature support.
- `MpdServerConfig` supports TLS and certificate/password auth in type shape.
- `sotf-player` has a headless `run_server_mode` that loads the library and starts MPD/DLNA servers if configured.

Main gaps:

- `run_server_mode` never builds a `sotf-tls` certificate store, never constructs a TLS acceptor, and never passes `trusted_client_fingerprints` into `sotf-mpd`.
- If `sotf-mpd` is compiled with the `tls` feature and config has `tls_enabled=true`, the server refuses to run without an acceptor. If it is compiled without that feature, the TLS config is effectively fiction.
- MPD is control/browse, not an audio-serving protocol for a native mobile player. It is useful for compatibility, but it cannot be the whole SOTF remote-player API.

### DLNA MediaServer

Relevant code:

- `crates/sotf-server/crates/sotf-dlna/src/server.rs`
- `crates/sotf-player/src/server.rs`

What works:

- The MediaServer advertises via SSDP, handles `ContentDirectory` browse/search, and has a `/media/{id}` HTTP path.
- HTTP request reading is capped for headers and control bodies.

Main gaps:

- `DlnaLibraryAdapter` does not override `media_path`, so `/media/{id}` returns `501 Media streaming not implemented by this adapter`.
- The `/media/{id}` implementation reads the whole file into memory and does not support Range requests. That is not acceptable for large files or seeking.
- GENA eventing and SCPD endpoints return 501, which many strict controllers expect.
- DLNA is plain HTTP and multicast discovery. Good for LAN compatibility, bad for security-sensitive remote access.

### DLNA Renderer

Relevant code:

- `crates/sotf-server/crates/sotf-dlna/src/renderer.rs`

What works:

- A MediaRenderer control surface exists and maps AVTransport/RenderingControl actions to a `RendererAdapter`.
- It rejects non-HTTP(S) URIs to avoid obvious local-file schemes.

Main gaps:

- Headless server mode starts only a DLNA MediaServer, not a Renderer.
- There is no production adapter connecting renderer actions to the actual player.
- Scheme allow-listing is not enough SSRF protection if the renderer later fetches arbitrary private-network URLs.

### AirPlay and Chromecast

Relevant code:

- `crates/sotf-server/crates/sotf-cast/src/airplay.rs`
- `crates/sotf-server/crates/sotf-cast/src/chromecast.rs`
- `crates/sotf-server/crates/sotf-cast/src/discovery.rs`

What works:

- mDNS discovery for `_raop._tcp` and `_googlecast._tcp` exists.
- AirPlay and Chromecast sender types have basic state machines and audio-writing APIs.

Main gaps:

- Chromecast does not implement CASTV2 TLS, receiver launch, or media `LOAD`; it starts a local HTTP stream and logs the URL.
- AirPlay comments describe RAOP/AES/ALAC, but the code sends big-endian PCM RTP packets with a payload type/comment mismatch and no visible encryption/key exchange. Treat it as a prototype.
- Neither sender is integrated into the main player output pipeline as a supported output device.

### Peer TLS and Trust

Relevant code:

- `crates/sotf-server/crates/sotf-tls/src/*`

What works:

- Certificate generation, key storage, TOFU store, client verifier, and server-side pinned-client verifier exist.
- Key files are restricted on Unix and TOFU entries are persisted atomically.

Main gaps:

- The TLS crate is not wired into `sotf-player` server startup.
- There is no pairing ceremony: QR code, fingerprint display, accept/reject UI, mTLS client cert creation, or trust revocation flow.
- There is no SOTF-native service advertised over mDNS for discovery/pairing.

## Security, Firewall, and Ports

Principles:

- Default to local machine or LAN-only. Do not encourage WAN port forwarding.
- Bind to `127.0.0.1` for local-only control; require an explicit "LAN server" toggle for `0.0.0.0`.
- Require TLS + either mTLS pairing or a strong password for SOTF-native remote control.
- Keep DLNA plain HTTP as a compatibility mode with clear LAN-only labeling.
- Provide preflight checks before enabling a server: bind address, port availability, TLS state, fingerprint list, firewall likely-blocked status, and advertised local IP.

Ports/protocols to document:

- MPD-compatible control: TCP 6600 by default.
- Future SOTF HTTPS API/media service: choose one TCP port, preferably separate from MPD, with mDNS advertisement.
- DLNA MediaServer HTTP: TCP 8200 by default.
- SSDP discovery: UDP multicast 239.255.255.250:1900.
- mDNS discovery/cast discovery: UDP 224.0.0.251:5353.
- Chromecast/AirPlay: mostly outbound discovery/control from SOTF, plus ephemeral local HTTP if Chromecast streaming remains HTTP-pull based.

Platform notes:

- macOS: document the System Settings firewall flow and code-signing requirement. A packaged app should request/allow incoming LAN connections intentionally, not by asking users to run random commands.
- Windows: provide a generated `netsh advfirewall firewall add rule ... protocol=TCP dir=in localport=<port> action=allow` command for advanced users, but prefer an app-managed prompt/installer rule.
- Linux: document `ufw allow <port>/tcp`, `firewall-cmd --add-port=<port>/tcp`, and multicast requirements.
- iOS/iPadOS: local network access requires `NSLocalNetworkUsageDescription`; Bonjour browsing requires `NSBonjourServices`; multicast features may need the multicast networking entitlement depending on implementation.

## What Must Change for a Good iPhone/iPad Player

The iOS app is currently a local GPUI shell with background audio, document import, route/interruption handling, and Now Playing metadata. That is a useful start, but not a networked SOTF player yet.

Required product shape:

- The iPhone/iPad should work first as a remote control for a desktop/server SOTF instance.
- It should optionally play server-hosted audio locally over HTTPS/range, but that should be a deliberate mode with buffering, cache, and battery handling.
- Paid service playback on iOS should use provider-approved native SDKs where required, even if that means the service does not pass through the SOTF DSP engine.

Required changes:

1. Add local network capability plumbing.
   - Add `NSLocalNetworkUsageDescription` and `NSBonjourServices` to the iOS `Info.plist`.
   - Define SOTF Bonjour service types, e.g. `_sotf._tcp`, plus any browsed services such as `_mpd._tcp`, `_raop._tcp`, and `_googlecast._tcp` if the app directly discovers them.
   - Add entitlement handling if multicast browsing is used.

2. Add discovery and pairing.
   - Advertise desktop/server instances over mDNS with name, version, TLS fingerprint, and capabilities.
   - Provide manual host entry for networks blocking multicast.
   - Add QR-code pairing from desktop to mobile.
   - Store accepted server certs and mobile client certs in Keychain/config, with revocation UI.

3. Add a SOTF-native remote API.
   - MPD is not enough for a native iOS experience.
   - Add HTTPS API endpoints for library browse/search, queue operations, playback state, volume, output devices, plugin presets, room/headphone EQ status, and server capabilities.
   - Add WebSocket or SSE for state/event updates: playback position, queue mutations, scanner progress, stream metadata, server health, and errors.
   - Add a media endpoint with Range support for "play on this iPhone/iPad".

4. Finish iOS playback integration.
   - Drain `RemoteCommand::NextTrack`, `PrevTrack`, and `ImportFiles` in the GPUI/AppState loop.
   - Keep Now Playing metadata synchronized with queue changes and remote server state.
   - Handle background audio, interruptions, route changes, AirPlay route selection, and lock-screen seek consistently.
   - Implement gapless/crossfade rules that work for local files, server streams, and supported provider SDKs.

5. Add a mobile-first UI model.
   - Fast server picker and connection state.
   - Library search that handles classical metadata.
   - Queue, now playing, output device, and volume controls reachable with one hand.
   - Clear mode labels: "Playing on Mac", "Playing on this iPhone", "Controlling Spotify", "DLNA compatibility mode".

6. Add offline/cache.
   - Cache album art and library index.
   - Support downloaded local imports.
   - For server-hosted audio, add an explicit local cache policy.
   - For paid services, only offer offline behavior permitted by that provider's SDK/terms.

7. Move secrets out of JSON.
   - Use Keychain on iOS/macOS and platform credential stores elsewhere.
   - Keep `servers.json` and source config for non-secret metadata only.
   - Add credential migration/redaction tests.

## Implementation Plan

### P0: Make Existing Server Modes Honest and Safe

Outcome: enabling a server never silently exposes an insecure or nonfunctional service.

Changes:

- Wire `sotf-tls` into `sotf-player::run_server_mode`:
  - load/generate server cert;
  - build TLS acceptor when `mpd.tls_enabled`;
  - pass `trusted_client_fingerprints` into mTLS config;
  - fail with a user-readable preflight error when certificate auth is selected but no trusted clients exist.
- Make the `sotf-mpd/tls` feature part of the player build path when server TLS is exposed in UI.
- Add server preflight diagnostics:
  - bind address and port availability;
  - TLS mode actually active;
  - auth mode valid;
  - local IP used for advertisement;
  - DLNA media serving implemented or disabled.
- Change UI copy from "MPD uses TLS" to a live status derived from the preflight result.
- Add tests for TLS config conversion and trusted fingerprint propagation.

Acceptance criteria:

- `sotf --server` with default TLS config either starts encrypted or refuses to start with an actionable message.
- A plaintext MPD server can only be started when the user explicitly disables TLS.
- Server settings show the actual exposed protocols and ports.

### P1: Make Streaming Out Real

Outcome: another machine can actually play a track from this SOTF library on the LAN.

Changes:

- Implement `DlnaLibraryAdapter::media_path`.
- Replace whole-file `/media/{id}` reads with streaming file I/O.
- Add HTTP `Range`/`HEAD` support and correct `Content-Range`, `Accept-Ranges`, MIME, and DLNA headers.
- Add stable media IDs that cannot be confused by album title collisions.
- Add a SOTF-native HTTPS media endpoint:
  - `GET /media/{track_id}` with Range;
  - token- or mTLS-authenticated;
  - no path leakage;
  - optional transcoding later, but source-quality first.
- Add docs for firewall ports and LAN-only DLNA.

Acceptance criteria:

- VLC/BubbleUPnP can browse and play a local FLAC from SOTF DLNA MediaServer.
- A second SOTF instance can play the same track through the SOTF HTTPS media endpoint without using MPD `httpd`.
- Large files do not allocate into memory as a whole.

### P2: Make Streaming In Robust

Outcome: remote libraries and service streams are usable sources, not isolated prototypes.

Changes:

- MPD peer:
  - implement TLS client support for `MpdClientAuthMode::Ssl`;
  - add secure out-of-band credential lookup for `MpdStreamSource`;
  - stop clearing the remote queue as the long-term streaming strategy; prefer direct SOTF media endpoint for SOTF peers.
- HTTP/radio:
  - surface ICY metadata events to the player UI;
  - add source-level timeout/retry config;
  - add redirect and content-type policy.
- HLS:
  - implement media playlist fetching, segment buffering, discontinuity handling, and seek mapping;
  - add tests with local fixture playlists.
- DLNA input:
  - add response size caps;
  - add stricter URL parsing or an HTTP client library;
  - add event/poll refresh strategy.
- Services:
  - add federation providers for Tidal/Spotify only when features are enabled;
  - resolve service tracks into `AudioSource::Url`, native SDK handoff, or `PcmStream` deliberately;
  - add credential/session persistence through secure stores.

Acceptance criteria:

- Adding an MPD/SOTF peer, DLNA server, ICY station, and Tidal/Spotify source through the UI produces visible searchable/browsable content or a precise unsupported message.
- Playback failures distinguish auth, subscription, region, network, unsupported format, and provider-policy errors.

### P3: Add SOTF Remote API and Pairing

Outcome: iPhone/iPad and desktop clients have a modern API instead of reverse-fitting everything through MPD.

Changes:

- Define a versioned SOTF Remote API:
  - `GET /capabilities`;
  - `GET /library/search`;
  - `GET /albums/{id}`;
  - queue CRUD;
  - playback commands;
  - output device selection;
  - current state;
  - media Range endpoint;
  - event stream.
- Advertise `_sotf._tcp` over mDNS with TXT records for version, TLS required, pairing required, and friendly name.
- Add pairing:
  - desktop displays QR/fingerprint;
  - mobile scans/enters;
  - mobile creates/stores client cert;
  - desktop stores trusted client fingerprint.
- Add threat model tests:
  - unknown client rejected;
  - changed server cert warns;
  - revoked client denied;
  - LAN attacker cannot use plaintext fallback.

Acceptance criteria:

- A fresh iPhone app can discover, pair, browse, control playback, and receive live state updates from a desktop SOTF server without manual config.

### P4: Build the iPhone/iPad Player Experience

Outcome: the mobile app feels like a real player, not a desktop UI squeezed onto glass.

Changes:

- Add iOS network privacy keys and Bonjour service declarations.
- Add server picker, pairing screens, and connection diagnostics.
- Add native screens for:
  - Now Playing;
  - queue;
  - search/library;
  - album/work detail;
  - output device and volume;
  - downloads/cache;
  - server settings/trust.
- Wire remote commands into AppState queue actions.
- Add "play on server" and "play on this device" modes.
- Add background playback and state restoration tests on device/simulator where possible.

Acceptance criteria:

- Common phone tasks take one or two taps: connect, search, play, pause, skip, seek, change output, inspect queue.
- Lock-screen controls and Now Playing stay correct for local, server, and supported provider playback.

### P5: Classical and Paid-Service Roadmap

Outcome: classical streaming is treated as a metadata and rights problem, not just another URL.

Changes:

- Extend schema/model for classical entities:
  - work;
  - movement;
  - composer;
  - conductor;
  - ensemble/orchestra;
  - soloists;
  - label;
  - catalog number;
  - recording date;
  - release date;
  - multi-work albums.
- Apple Music/Classical:
  - use MusicKit for Apple-platform catalog/playback;
  - expose a mode that controls native playback rather than promising DSP of protected streams.
- Qobuz:
  - pursue partner/API access before implementation;
  - only add a provider once credentials, terms, and playback rights are clear.
- Tidal:
  - reconcile code with current official SDK/API and subscription rules.
- Spotify:
  - keep iOS App Remote as the mobile route;
  - keep librespot desktop/server support feature-gated and explicitly non-core until policy is reviewed.

Acceptance criteria:

- Classical search can answer "Bach Cello Suites Fournier", "Mahler 5 Abbado", "Ravel La Valse orchestration", and "Beethoven Op. 131 movement IV" without treating every movement as an unrelated pop track.
- Provider integrations never require storing raw passwords in source JSON.

## Test and QA Matrix

Server:

- MPD plaintext disabled/enabled intentionally.
- MPD TLS/mTLS happy path and unknown-client failure.
- DLNA browse/play with VLC/BubbleUPnP.
- SOTF-to-SOTF HTTPS media play with Range seek.
- SSDP/mDNS discovery on macOS, Windows, and Linux.
- Firewall-blocked and port-in-use diagnostics.

Streaming:

- HTTP seekable FLAC/MP3.
- ICY live stream with title updates.
- HLS VOD and live fixtures.
- Remote MPD with and without password.
- Tidal/Spotify feature builds disabled and enabled.

iOS:

- Local network permission prompt appears with useful text.
- Discovery works after permission grant; failure state is clear after denial.
- Pairing persists across launch.
- Background audio, interruptions, route changes, lock-screen controls, and seek.
- iPhone portrait, iPhone landscape, iPad split view, iPad landscape.

Security:

- No credentials in logs.
- No credentials in `servers.json` or source config JSON after migration.
- Unknown client cert rejected.
- TOFU changed-fingerprint warning blocks connection until user accepts.
- DLNA renderer refuses dangerous schemes and private-network SSRF once fetching is implemented.
